## Manual Cloudflare dashboard procedure

1. No dashboard change is currently required to fix the observed HTTP gap. If enforcement regresses, select the `gotechsonic.com` zone. Record current settings and export/capture existing Single Redirects, Bulk Redirects, Page Rules, configuration rules, Worker/custom-domain mappings, and any origin redirects before editing. Inspect both apex and www DNS entries and confirm traffic is proxied/served through Cloudflare; do not replace records or disturb mail records. Confirm active edge certificates cover both hostnames.
2. Open **SSL/TLS → Overview**. Encryption must not be Off. If an external origin is used, verify its certificate before choosing Full (strict); avoid Flexible with origin HTTPS redirects. Workers-hosted assets do not require inventing an external origin or changing DNS.
3. Open **SSL/TLS → Edge Certificates → Always Use HTTPS** and confirm it is **On**; enable it manually only if disabled. Review the zone-wide effect on other subdomains first. Automatic HTTPS Rewrites is not a substitute: the requirement is a response redirect before serving HTTP content.
4. Retain the working apex-to-www rule described above. If a future reviewed change seeks a direct hostname conversion on either protocol, use one authoritative rule under **Rules → Redirect Rules → Single Redirects**, matching `(http.host eq "gotechsonic.com")`. Use a **Dynamic** destination expression `concat("https://www.gotechsonic.com", http.request.uri.path)`, status **301**, and **Preserve query string: Enabled**. Do not use a fixed homepage destination or append the query manually as well as enabling query preservation. This optional configuration was not applied.
5. Place the apex redirect before conflicting rules; use Cloudflare Trace to confirm which rule actually executes. Remove/disable overlapping rules only after review. No rule may redirect HTTPS www back to apex or HTTP, and the canonical destination must not match the apex rule. Avoid adding another application/origin redirect for the same conversion.
6. Test before declaring completion. Prefer one hop from either noncanonical hostname/protocol to HTTPS www. If Always Use HTTPS upgrades HTTP apex before the hostname rule executes, a two-hop chain (`http://apex` → `https://apex` → `https://www`) is acceptable; do not promise one hop without Trace/live evidence. More than two protocol/hostname hops, any loop, or a final HTTP/apex destination fails acceptance. Existing trailing-slash normalization may add a separate path redirect; use canonical paths in this test.

Always Use HTTPS plus the apex rule is sufficient; do not add a third broad redirect matching the canonical destination. Roll back only the newly changed setting/rule to its captured value if validation fails, then investigate the conflict before retrying. HSTS/preload is outside this change and is not required to fix HTTP redirects.

Cloudflare references: [Always Use HTTPS dashboard procedure and limitations](https://developers.cloudflare.com/ssl/edge-certificates/additional-options/always-use-https/), [hostname redirects with path/query preservation](https://developers.cloudflare.com/rules/url-forwarding/examples/redirect-all-different-hostname/), and [Single Redirect settings](https://developers.cloudflare.com/rules/url-forwarding/single-redirects/settings/).

## Path/query acceptance checks

Run read-only GET checks from a network that resolves the production domain, after the dashboard changes. Use curl rather than relying on a browser's cached 301 or HSTS upgrade. For each of the four origins, test `/` and `/contact?utm_source=seo-audit&next=%2Ftools%3Ftab%3Dsla&tag=one&tag=two`.

```powershell
$origins = @('http://gotechsonic.com', 'http://www.gotechsonic.com', 'https://gotechsonic.com', 'https://www.gotechsonic.com')
$paths = @('/', '/contact?utm_source=seo-audit&next=%2Ftools%3Ftab%3Dsla&tag=one&tag=two')
foreach ($origin in $origins) {
  foreach ($path in $paths) {
    curl.exe --silent --show-error --path-as-is --location --max-redirs 2 --connect-timeout 10 --max-time 30 --output NUL --dump-header - --write-out 'final=%{url_effective} status=%{http_code} redirects=%{num_redirects}\n' "$origin$path"
    if ($LASTEXITCODE -ne 0) { throw "Redirect verification failed for $origin$path" }
  }
}
```

Inspect every `Location`, final URL, status and redirect count. All eight final URLs must equal `https://www.gotechsonic.com` plus the original path/query exactly, with final status 200. Preserve encoding, repeated parameters, and order; no path may collapse to `/`. Canonical HTTPS www should have zero redirects for these canonical paths. The command limits chains and reports evidence; the URL/status assertions require review. Also test a representative asset and `sitemap.xml` to confirm edge coverage beyond HTML. Do not submit API POSTs as redirect probes. Save response headers and Cloudflare Trace output with the release evidence.

## React/Vite static rendering

Before V2.5, route HTML had unique metadata but an empty app root. The build now loads the existing route components through Vite's SSR module loader, resolves all page modules first, and uses React `renderToString` to generate content for each public path, including `/`. It fails if a route emits the loading shell or lacks its H1. Using the actual components avoids a separate SEO-only copy of content. No browser, production data fetch, Worker execution, or secret is needed to prerender.

The frontend retains lazy route chunks. `hydrateRoot` attaches interactivity to matching prerendered paths; development and unknown SPA fallback paths use `createRoot`. Contact query parameters use a hydration-safe server snapshot and are applied after hydration, preserving existing category/context prefills. Tests hydrate all ten routes without replacing their static H1 or producing recoverable hydration errors, and cover query-prefilled contact hydration.

News still fetches cached data in the browser; its heading, explanation and primary-source links are in static HTML, while live articles remain dependent on JavaScript and the API. The advisor remains lazy and user-activated. Turnstile/Brevo retain their existing flow. No live provider requests or inquiry submissions are part of static generation.

Known limitation: existing Cloudflare SPA fallback still serves the homepage document for unknown URLs before JavaScript renders the not-found view. Client metadata now marks unknown routes `noindex, follow`; a true server-side 404 requires a separately reviewed asset/Worker fallback change. Matching-path hydration guards prevent hydrating the homepage as another route. No public route in the ten-route inventory is affected.

### Consent and visitor choices

The accessible interface offers equally prominent **Accept** and **Reject**, plus **Manage preferences**. A native modal dialog provides keyboard focus containment and Escape dismissal; closing it grants no consent. A permanent preferences control and crawlable privacy disclosure appear on every page. The banner is shown only in an enabled environment while the choice is unknown; disabled builds still expose preferences and explain that a saved choice does not activate tracking.

Basic Consent Mode v2 is used: no Google tag, preconnect, queue, cookie or event before opt-in. Upon an eligible grant, the command queue starts with all four storage/ad consent states denied, then grants only `analytics_storage`. `ad_storage`, `ad_user_data` and `ad_personalization` remain denied; Google signals and ad personalization are disabled. This avoids advanced-mode cookieless pings before consent.

Consent choice/version/expiry is stored in `localStorage` under `techsonic.analytics-consent.v1`, for up to 180 days. Invalid/expired records fail closed. Storage failures allow a per-visit choice and show a notice without breaking the site. Rejection is remembered. Withdrawal sets Google's disable flag immediately, removes the tag and queued commands, expires this integration's `_ga` and `_ga_3SSEPPT5TK` cookies on host/parent domains, and reloads without the tag to unload its listeners. Cross-tab withdrawal also stops and reloads an active tab. Previously consented requests/data cannot be recalled by withdrawal. Tag-load failure/timeout disables optional analytics without interfering with page functionality.

The on-site disclosure describes Google cookies/technical data processing, fixed activity categories, exclusions, choice retention and withdrawal. Inquiry consent remains separate. This is an engineering implementation, not a claim of compliance with every applicable privacy/consent law; the owner must review applicable jurisdictions, wording, Google data retention/access settings and request-handling obligations before activation.
